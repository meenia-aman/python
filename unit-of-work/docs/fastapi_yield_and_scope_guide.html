FastAPI Dependencies with Yield & Scope

Understand how FastAPI turns generators into context managers, the critical difference between scope="function" and scope="request", and how Module 1's explicit Unit of Work compares with Module 3.

The Anatomy of a Yield Dependency

In standard Python, a function with yield is a generator. FastAPI uses Python's contextlib.asynccontextmanager and AsyncExitStack internally to transform that generator into a two-phase execution lifecycle wrapped around your endpoint. 

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    # ────── [PHASE 1: BEFORE YIELD] ──────
    # Runs BEFORE the route handler executes
    session = AsyncSessionLocal()
    try:
        yield session  # <── Injected into your route handler!
        
        # ────── [PHASE 2: AFTER YIELD] ──────
        # Runs AFTER the route handler returns
        await session.commit()
    except Exception:
        await session.rollback()
        raise
    finally:
        # Always runs guaranteed
        await session.close()

Phase 1: Before yield

Runs when the incoming request arrives at FastAPI before calling your route function:

  • Connects to the database / checks out a session from the connection pool.
  • Optionally starts a transaction via session.begin().
  • The yielded object (session) is passed as the argument to the path operation function.

Phase 2: After yield (Teardown)

Runs after the route handler has executed:

  • If the route handler succeeded: executes the lines immediately following yield (e.g. commit()).
  • If the route threw an error: FastAPI re-raises that error into the generator at the yield point, triggering except Exception: and rolling back!
  • In finally:, the session is cleanly closed.
💡
How Context Managers work inside Yield:
In Module 3, we wrote: 
async with AsyncSessionLocal() as session:
    async with session.begin():
        yield session
FastAPI enters both context managers before yield. When the endpoint finishes, FastAPI resumes the generator, causing Python to exit session.begin() (which commits!) and exit AsyncSessionLocal() (which closes the connection!).
⚠️
The Critical Difference: When does teardown execute?
In FastAPI 0.115+, dependencies support scope="function" vs scope="request" (the default). The choice determines whether database commits happen before or after the client receives the HTTP response!

scope="function"

Module 3 Standard

The dependency teardown runs before the HTTP response is dispatched to the client.

1

Setup (Before Yield) Phase 1

Opens AsyncSession.

2

Route Handler Endpoint

Executes order logic, returns dict/schema.

3

Teardown (After Yield) Phase 2

Commits transaction & closes session NOW!

4

Response Sent to Client HTTP Send

If commit succeeded: 200 / 201 OK
If commit failed: 500 Error

✅ Completely Safe: Client is never sent false success if commit crashes.

scope="request" (Default)

Dangerous for Commits

The dependency teardown runs after the HTTP response has already streamed to the client.

1

Setup (Before Yield) Phase 1

Opens AsyncSession.

2

Route Handler Endpoint

Executes order logic, returns dict/schema.

3

Response Sent to Client HTTP Send

Client ALREADY received 200 OK!

4

Teardown (After Yield) Phase 2

Commits transaction. If commit fails, it's too late!

❌ Risky: Client thinks order succeeded, but DB rolled back!

Characteristic scope="function" scope="request" (Default)
When does code after yield run? Immediately after endpoint returns, before HTTP response is sent. After response headers and body are fully sent to the client.
What if session.commit() fails? FastAPI catches exception and sends HTTP 500 to the client. Client already got HTTP 200. Server logs an unhandled error later.
Dependency caching (use_cache=True) Caches within the function call graph. Caches across the whole request.
Best use case Database transactions, Unit of Work, write operations. Read-only resources, client metrics, request-duration loggers.

Architecture Comparison: Module 1 vs Module 3

Both modules achieve atomic transactions across multiple repositories (Orders, Products, Emails, Users), but they do it in different architectural layers:

Module 1: Explicit Unit of Work

Managed directly in your Python code via a custom class:

# In OrderService
async with self.uow:
    user = await self.uow.users.get(user_id)
    product = await self.uow.products.get(prod_id)
    product.stock -= count
    await self.uow.orders.add(order)
    await queue_email(self.uow.emails, ...)
    
    await self.uow.commit()  # Explicit call!
  • Who owns transaction: The Service class.
  • Pros: Completely independent of FastAPI; easily runs in Celery workers, cron jobs, CLI scripts.
  • Cons: Requires custom UoW classes (`UserUnitOfWork`, `OrderUnitOfWork`) for every domain combination.

Module 3: Dependency-Owned Transaction

Managed by FastAPI's dependency injection using yield & function scope:

# In src/module_v3/db.py
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        async with session.begin():
            yield session

SessionDep = Annotated[AsyncSession, Depends(get_db, scope="function")]
  • Who owns transaction: The HTTP API operation boundary.
  • Pros: Zero boilerplate UoW classes; services never worry about calling commit/rollback.
  • Cons: Tied to FastAPI's dependency system; background workers need their own transaction context.

The Dilemma: There is No FastAPI Request in Celery/Background Workers

In Celery, ARQ, Kafka consumers, or CLI scripts, FastAPI's dependency injection does not run. If our services no longer commit, who owns the transaction in a background worker?

💡
The Golden Rule: "Services never commit. The CALLER (boundary) owns the transaction."
In HTTP, the caller is SessionDep (FastAPI). In a worker, the caller is an async context manager (transaction_scope()).

1. Reusable Transaction Scope Context Manager

Define a clean context manager in db.py:

from contextlib import asynccontextmanager

# The Universal Transaction Boundary
@asynccontextmanager
async def transaction_scope():
    async with AsyncSessionLocal() as session:
        async with session.begin():
            yield session
        # Automatically commits on exit!
        # Automatically rolls back if an exception escaped!

2. Composition Factory Helper

Create a single helper that builds your service graph with any session:

def build_order_service(session: AsyncSession) -> OrderService:
    return OrderService(
        order_repo=SqlAlchemyOrderRepository(session),
        user_service=UserService(SqlAlchemyUserRepository(session)),
        product_service=ProductService(SqlAlchemyProductRepository(session)),
        email_service=EmailService(SqlAlchemyEmailRepository(session)),
    )

How to use it in Background Workers / Celery:

@celery_app.task
async def process_order_worker(order_payload: dict):
    # The worker opens the transaction boundary!
    async with transaction_scope() as session:
        service = build_order_service(session)
        await service.create_order(CreateOrderRequest(**order_payload))
    
    # ✅ Automatic atomic commit here.
    # ❌ If anything failed, rollback was executed automatically.

How FastAPI uses the EXACT same function:

async def get_db():
    async with transaction_scope() as session:
        yield session

SessionDep = Annotated[AsyncSession, Depends(get_db, scope="function")]

@router.post("/orders")
async def create_order_endpoint(data: CreateOrderRequest, session: SessionDep):
    service = build_order_service(session)
    return await service.create_order(data)
🎯
Result: Zero code duplication! Both the HTTP API and the Background Worker share the exact same business logic, the exact same single-commit guarantee, and the exact same rollback-on-error safety.
